## What the proposed hierarchy means

`CATEGORY_AUDIT_CONSOLIDATION_PLAN.json` gives every one of the 113 discovery leaves
exactly one proposed reporting parent. The parent includes/excludes and boundary
rules are substantive proposals derived from the existing training definitions.
The crosswalk keeps each original definition, seed, candidate set and current
evidence status. Parent membership does not declare leaf mechanisms equivalent.

Use the hierarchy to review related obligations together, retaining the leaf as the
specific mechanism. Do not substitute a broad consequence such as “exception” for
the actual encoding, context, validation or algorithmic defect. Do not pick a target
category count or consolidate to meet a support floor. Counts come after the
definitions, not the reverse.

Particular decisions:

- A native scalar exporter must preserve native values; a text writer must convert
  them. They can share a representation parent without sharing an expected result.
- Metadata preservation and invalidation are separate, sometimes opposite duties.
  A transformation does not always preserve or always drop metadata.
- The broad incomplete-case, state-transition and context labels need the specific
  admitted input, starting/target state or producer/consumer contract for each pair.
  Existing broad assignments are not automatically changed by the crosswalk.
- Browser method gating, CSRF binding and credentialed CORS enforce different
  policies. A fix in one must not inherit a complete claim about the others.
- Informational output can be functional: malformed error-result tuples can prevent
  error recording, and subprocess initialization can re-enter a program. Establish
  the actual contract/path rather than automatically including or excluding logs.
- Security parents remain separate from correctness parents. An ordinary bug source
  is not a negative security finding, and a CVE is not selected-function attribution.

## Candidate decision record to prepare

The generated review queue covers **every training candidate**, including supported
ones. Its retrieval cues are literal excerpts from earlier notes, not new decisions.
Negated or hypothetical phrases can match. Follow the original evidence and inspect
the source when resolving a case.

Prepare these independent dimensions for each original ID:

| Dimension | Required determination |
|---|---|
| Mechanism | Identify the exact old behavior, preconditions, consumer and expected result. Retain a narrow discovery leaf or a justified proposed revision. |
| Existing contract | Cite evidence predating or otherwise establishing the requirement; distinguish a repair from an introduced feature or intentional policy/API revision. |
| Selected relevance | Show how this selected function contributes to that violation; distinguish equivalent refactors and coordinated new-interface plumbing from a locally evidenced defect. |
| Security domain | Establish an actual trust boundary/reachability for a security label; explicitly screen general-bug candidates rather than infer non-security status from provenance. |
| Function-only sufficiency | Decide whether the intended finding is justified from the common before-only input and ordinary API semantics, or critically depends on unavailable per-case caller/configuration/runtime facts. |
| After/negative scope | Establish whether the specified witnessed mechanism is repaired and whether another after defect invalidates a paired-negative use. No universal clean labels. |
| Representation overlap | Identify nested/outer copies, exact/AST versions and source overlap; choose a defensible experimental representation without deleting canonical records. |
| Issue identity | Propose a root-cause issue unit with evidence for aliases/backports/follow-ups; preserve dependency and repository descriptors separately. |
| Final proposal | Retain, unresolved or proposed subset exclusion, with exact reason/evidence. All researcher approval remains pending until explicitly supplied. |

An assistant-supported discovery finding is a starting mechanism hypothesis, not an
automatic “retain.” An ambiguous finding is not automatically a negative/exclusion.
An exclusion proposal can be reversed if an established contract is demonstrated.
Unknown dimensions must remain unknown rather than be converted into a score.

## Common bounded-input proposal

The primary detection task should retain a **single before-only bounded-function
input protocol shared across all compared conditions**. Prepare it as follows:

1. Start from the released before-only selected function, including the original
   function signature, body and retained decorators. Preserve its text/hash and
   record the actual model/tool input hash. Do not append the selected after code.
2. Specify and feasibility-check a common numerical input budget and deterministic
   over-budget policy **before freeze**. No numerical limit is certified by this
   proposal. Character/line counts are inventory measurements, not token counts;
   do not silently truncate away a required statement or use per-model truncation
   that changes the task. Any subset selection must retain original IDs and splits.
3. Treat ordinary language/API knowledge consistently, while recording any critical
   project-specific fact unavailable in the function. A note mentioning a helper
   does not by itself prove insufficiency; a missing actual policy/reachability
   premise must not be guessed. Resolve that distinction case by case.
4. For standalone static analysis, document the exact inert representation and any
   syntax-only wrapping/dedenting needed to parse it. Do not invent imports,
   bindings, caller stubs or definitions that add semantic evidence selectively.
   If selected nested code cannot be analyzed faithfully, record the limitation
   and eligibility decision. Guard against context-loss warnings being interpreted
   as original defects, and inspect alias/import-dependent tool detection.
5. Keep IDs, category/issue labels, commit/CVE metadata, advisories, fix diffs,
   tests/regression answers, reviewer reasoning and the consolidation queue outside
   detection input. The full evidence remains adjudication-only. The generated
   crosswalk/report/queue are not training examples or model prompts.
6. Freeze tool versions/rule filters, prompt/output schema and identical static
   findings supplied to each augmented LLM condition. The unchanged Qwen comparator
   must use matched quantization/settings where applicable; added context must not
   erase the ability to isolate adaptation. This consolidation step runs no models
   or tools against dataset programs.

Cases requiring facts outside this common condition remain unresolved for that
condition until a principled eligibility decision is recorded. Do not quietly
promote adjudication context into inputs to make difficult cases detectable. A
change to a bounded-context condition requires its own explicit common protocol
version and reevaluation of input equality and leakage before approval.

## Paired-negative rules

- Record a concrete old witness and which changed mechanism prevents it. Read tests
  as evidence, not as reproduced behavior. Source/AST inspection is not execution.
- A fixed branch can still fail on another boundary, mode, version or input. Keep
  that residual outside a narrowly justified negative only if it does not invalidate
  the actual intended paired task; otherwise propose unresolved/pair exclusion.
- Constant-time behavior, race freedom, comprehensive grammar, universal path
  confinement and absence of all security defects cannot be inferred from one fix.
- Do not use a shared advisory or tests for a companion function as evidence that
  this selected function is a repaired positive. Inspect helper/caller attribution.
- Do not modify canonical labels/source to repair an after-side regression. Record
  the problem and a proposed experimental-subset decision.

## Issue and dependence reconciliation

`CATEGORY_AUDIT_CONSOLIDATION_DEPENDENCE.json` retains the existing mechanical
families, source-overlap links, shared exact/AST versions, repeated function
histories and two manually specified, hash-verified follow-up chains. These are
review evidence, not independent issue identities.

1. Begin with the conservative existing same-fix/CVE/exact-pair family. Multiple
   changed functions or nested selected spans do not create new issues.
2. Check aliases, backports, forks and incomplete fixes against pinned provenance.
   Different CVE or commit identifiers do not automatically imply independence.
3. An after-to-before match establishes a shared version, not chronology or the same
   defect. The curated Thefuck chains additionally have retained fix/context
   evidence, but their root-cause issue split still needs explicit adjudication.
4. Repeated function identity can involve unrelated later defects. Do not blindly
   merge issue labels because they share a function, or regard successive fixes as
   independent simply because their mechanical family IDs differ.
5. Connected dependence-review blocks intentionally organize conservative review.
   They are neither automatically proposed issue merges nor a statistical proof
   of independence. Repository dependence can remain between disconnected blocks.
6. If one commit covers multiple roots, preserve the conservative family until
   evidence supports a split. If one issue has multiple fixes, retain a single
   proposed root-cause identity with its fix variants and affected functions.
7. Add an explicit, validated adjudication record format before recording approved
   issue counts. The current ledger intentionally permits pending assistant
   decisions only. Researcher confirmation must never be manufactured from these
   generated links, support counts or broad category parents.
